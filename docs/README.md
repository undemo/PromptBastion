# 技术部分

## 项目概述

基准模型：Qwen2.5 7B Instruct

运行环境：内存>=32GB,显存>=30GB

### 核心功能

- 🚪 **门卫模块**：使用大模型微调实现，对用户输入进行初步分类筛选
- 🔍 **政审模块**：使用 prompt 实现，识别涉政涉军敏感内容
- 🔤 **敏感词模块**：使用敏感词库，检测并处理敏感词汇，将敏感词加入到输入 prompt 之前
- ✅ **自审查模块**：使用 prompt 实现，对AI生成的回答进行安全审查
- 🧹 **数据净化模块**：调用本地或外部 API，对回答进行最终净化处理
- **两种回答模型**：一种是原生 Qwen2.5 7B Instruct，一种是使用政治军事回答来特训版的回答敏感问题的”政治“大模型

## 安全模块详解

### 1. 门卫模块 (Doorkeeper)

**功能**：对用户输入进行初步分类，判断是否为恶意请求。

**处理流程**：
1. 调用 classify LoRA 进行分类
2. 调用外部 API 裁判进行二次判断
3. 双重裁判机制：双方一致才有效，否则放行

**分类结果**：
- `good` / `jailgood`：安全输入，放行
- 其他：可能的恶意输入

### 2. 政审模块 (Political Review)

**功能**：识别涉政涉军敏感内容，决定是否使用政治版模型。

**分类结果**：
- `Irrelevant`：非敏感领域，使用原版模型
- `Foreign`：明确指代外国，使用原版模型
- `China`：明确指代中国，使用政治版模型
- `Ambiguous`：指代不清，使用政治版模型

### 3. 敏感词模块 (Sensitive Words)

**功能**：检测用户输入中的敏感词汇。

**处理方式**：
- 检测到敏感词时，在用户输入前添加警告提示
- 不直接拒绝，而是提醒模型注意回答的合法性

### 4. 自审查模块 (Self Review)

**功能**：对 AI 生成的回答进行安全审查。

**评估标准**：
- `harmful=0`：回答可能有害，拒绝
- `harmful=1`：回答安全，通过

### 5. 数据净化模块 (Data Purification)

**功能**：对最终回答进行净化处理。

**处理内容**：
- 移除不当表述
- 确保语言规范礼貌
- 保持核心内容不变

## 大模型微调

使用 llama factory 来进行微调，需要准备大量的语料库，将 loss 降到 1 左右最合理（不是越低越好）。

## 下一步的优化方向

1.增加模板记忆匹配机制，动态适应不断优化更新的模板

2.优化政审、自审查提示词，根据更多数据优化一版更好的提示词

3.关于门卫，可以使用比较小的 0.7B 模型，可以在大大优化体积、显存占用的情况下取得相对较好的效果

4.把基础回复模型和系统解耦合，可以在后台自己设置回复的模型路径（本地或远程 API），更符合实际生产环境

# 关于比赛

## 失败原因总结

虽然我到现在依旧认为，我们队伍最后没有取得成绩的原因在于赛事方的无理取闹，不专业无纪律，但是如果抛去这一切，还是有值得思考的一些地方。

### 一、最开始的技术基座设计不牢

回想这次比赛，从一开始的决定报名，到技术架构的提出，到最终的成果，发现最终留下遗憾的一个关键原因在于：**技术构想和技术实现没有清晰的拆开**，从最开始的调研阶段，以及各位队员想法的提出，到最后亲自去实践落地，这其中的时间点并没有一个清晰的切分。导致给我的感觉像是一直在做实验，没有平稳的向下推进的感觉。

因此，如果未来还有类似的机会，一定要明确：什么阶段属于技术畅享阶段，什么阶段属于需要平稳落地的阶段。

### 二、代码编写不规范

由于部分使用了 AI coding，且没有及时、按规范的进行代码审计，导致最后的代码乱做一团，每次修改一个小的功能，都要很大程度上从一团乱麻的代码中精准的去找出要修改的部分，这无疑是一个巨大的工作量，大大拖慢了进度，也增添了很多未知的 bug（我怀疑最后的复赛有部分超时、回答不好就是因为此）

![image-20251201190706699](https://img.undem.cn//202512011907747.png)

2000 行代码塞在一个文件里，代码冗余程度可见一斑。

### 三、成员任务分配不合理

由于缺乏管理经验以及项目经验，导致我始终觉得我们队伍的每个人角色分配不明确，更大的感觉像是：我需要一个人去帮我做一个事情，然后去私聊某位成员去完成。这是十分不合理的，很可能导致一个团队的有些成员很忙，有些成员很闲。

今后应该为每个成员设置详细的任务，且不能是一个宽泛的，很久不“活跃”的任务，必须是可频繁交互的任务，这样才能保证成员对于项目的积极性和参与感

## 四、一些开发经验

在这次比赛中，我分别尝试了前端->后端、后端->前端，发现效果都不尽如人意。不仅开发效率低，而且还会频繁的发生各种 bug。现在我思考的一个比较合理的开发路径为：先开发接口文档，再根据接口文档开发前后端，并及时做好 git 的版本记录，并需要有专人对此做出维护，这样才能增加条理性，不至于到后期手忙脚乱。
